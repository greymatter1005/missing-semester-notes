Debugging and Profiling

Code does what you tell it to, not what you expect. Tools for closing that gap — from print statements and debuggers to time-travel debugging, sanitizers, profilers and flame graphs.

Two halves. Debugging — code that gives the wrong answer. Profiling — code that gives the right answer but burns too much CPU, memory or time. Measure before you optimize: premature optimization is the root of all evil.

01Print debugging & logging

Brian Kernighan's advice still holds: careful thought plus well-placed print statements is the most effective debugging tool. Add prints near the problem; iterate until you understand it.

Logging is “printing with more care”, through a framework that gives you:

📍 Destinations

Send logs (or a subset) to files, the console, a log service…

🎚 Severity levels

DEBUG, INFO, WARN, ERROR — and filter by level.

🧾 Structured data

Key–value fields you can search and extract later.

🎚 Filter by severity — show this level and above
♻️
Turn fixes into logs. Once a print helped you find a bug, convert it into a proper log statement instead of deleting it — next time the diagnostics are already there.
📜
Other programs' logs: try -v / --verbose (often repeatable for more detail), look in /var/log/, use journalctl -u <service> for systemd services, and check libraries for debug-logging environment variables.

02Debuggers

Reach for a debugger when you don't know what to print, the bug is hard to reproduce, or restarting is expensive. Debuggers let you pause at a line, step one instruction at a time, inspect variables (even after a crash) and break on conditions.

General-purpose

gdb (GNU) and lldb (LLVM) debug any native binary — the standard for C, C++, Rust. They expose registers, stack, program counter and more.

Language-specific

Python's pdb, Java's jdb — tighter integration with the runtime.

gdb commandDoes
runStart the program
b func · b file:lineSet a breakpoint
cContinue to the next breakpoint
step / next / finishStep into / over / out of a function
p varPrint a variable
btBacktrace (call stack)
watch exprStop when a value changes

Tip: gdb -tui (or Ctrl+x a inside gdb) shows the source beside the prompt. Compile with -g (debug symbols, DWARF) and ideally -fno-omit-frame-pointer, or stack traces may be just addresses.

Try it: find the merge-sort bug

This is the lecture's exercise. merge_sort([3,1,4,1,5,9,2,6]) should give [1,1,2,3,4,5,6,9]. We've paused in the first merge call that goes wrong. Click line numbers to set breakpoints, then step.

03Record–replay debugging with rr

Heisenbugs vanish when you look at them — races, timing bugs. A print can slow things enough to hide the race. rr (Linux) records one execution, then replays it deterministically, as often as you like, inside gdb — and lets you run backwards.

bash
rr record ./my_program   # record once
rr replay                # replay in gdb
Reverse commandRuns backwards…
reverse-continue (rc)to the previous breakpoint / watchpoint
reverse-step (rs)one line
reverse-next (rn)one line, over calls
reverse-finishto where this function was entered

The killer workflow: run to the crash → see the corrupted value → watch it → reverse-continue → land on the exact line that wrote it.

⏪ Time-travel the lecture's corruption.c

curve_scores(0, 5) only touches student 0 — yet student 1's id changes. Memory layout (each box = one int):

students[0]
students[1]
void curve_scores(int student_idx, int curve) {
    for (int i = 0; i < 4; i++) {          // scores has only 3 slots!
        students[student_idx].scores[i] += curve;
    }
}
⚠️
Caveats. rr serializes threads, so some races won't show under it — you may need several recordings to catch one (then it replays reliably). Linux only; needs hardware performance counters (not available in many VMs, e.g. most AWS EC2), no GPU support. On macOS, see Warpspeed.

Use rr for: flaky tests · race conditions · hard-to-reproduce crashes · any bug where you wish you could go back in time.

04System call tracing

Programs ask the kernel for everything — opening files, memory, processes. Watching those system calls shows why a program hangs, which files it touches, and where it waits.

strace (Linux) · dtruss (macOS)

bash
strace ./my_program                  # every system call
strace -e trace=file ./my_program    # only file-related calls
strace -f ./my_program               # follow child processes
strace -p <PID>                      # attach to a running process
strace -T ./my_program               # time spent in each call

bpftrace & eBPF

eBPF runs small sandboxed programs inside the kernel; bpftrace gives them an awk-like syntax. Use it when you need lower overhead, aggregation (counts, latency stats) or kernel-level detail. It runs as root and sees the whole system — filter by command or PID.

bash
# print every file opened, system-wide
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'

# count system calls by name (summary on Ctrl-C)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* { @[probe] = count(); }'

# only for bash
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* /comm == "bash"/ { @[probe] = count(); }'

# trace a command from startup (-c sets cpid)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* /pid == cpid/ { @[probe] = count(); }' -c 'ls -la'

For C-level eBPF there's bcc, which ships ready tools like opensnoop (open files) and biosnoop (disk latency). Julia Evans' strace zine is a friendly deep dive.

strace

Easiest to start with; one process; higher overhead.

bpftrace

Low overhead; kernel-wide; aggregation; needs root.

05Network debugging

bash
sudo tcpdump -i any port 80             # watch traffic on port 80
sudo tcpdump -i any -w capture.pcap     # save for Wireshark

HTTPS is encrypted, so tcpdump sees little. Use an intercepting proxy like mitmproxy — or, easiest for web apps, the browser's DevTools → Network tab (decrypted requests, headers and timing).

06Memory debugging

Buffer overflows, use-after-free and leaks rarely crash on the spot — they corrupt memory and blow up later, far from the cause.

Sanitizers (recompile, run, get a report)

SanitizerFlagCatches
AddressSanitizer (ASan)-fsanitize=addressBuffer overflows (stack/heap/global), use-after-free, use-after-return, leaks
ThreadSanitizer (TSan)-fsanitize=threadData races
MemorySanitizer (MSan)-fsanitize=memoryReads of uninitialized memory
UBSan-fsanitize=undefinedUndefined behaviour, e.g. integer overflow
bash
gcc -fsanitize=address -g program.c -o program
./program

Sanitizers are fast enough for everyday development and CI.

Valgrind (no recompiling)

Runs your program in a VM-like environment. Slower, but works when you lack the source, can't recompile (third-party libraries) or need a tool sanitizers don't offer.

valgrind --leak-check=full ./my_program

07AI for debugging

Where LLMs shine

• Translating cryptic errors (C++ templates, Rust borrow checker)
• Crossing language boundaries (a C library bug surfacing through Python, FFI, build systems, “I think it's my dependency”)
• Linking vague symptoms to causes (“10× more memory than expected”)
• Reading crash dumps and stack traces

Limits

• Plausible but wrong explanations (hallucinations)
• “Fixes” that hide the bug instead of fixing it
• Always verify with real debugging tools
• A complement to understanding your code — not a replacement

08Timing & resource monitoring

Simplest measurement: time it. But wall-clock time includes waiting. time splits it up:

bash
$ time curl https://missing.csail.mit.edu &> /dev/null
real    0m0.272s
user    0m0.079s
sys     0m0.028s
user 79 ms
sys 28
waiting on the network ≈ 165 ms

real

Wall-clock, start to finish, including waiting

user

CPU time running your code

sys

CPU time running kernel code for you

09Visualizing performance data

People spot patterns in plots far faster than in tables. So log tidily — 1705012345,42.5 (timestamp, value) or JSON plots instantly; a prose sentence doesn't.

bash
gnuplot -e "set datafile separator ','; plot 'latency.csv' using 1:2 with lines"

For exploration, Python's matplotlib and R's ggplot2 — ggplot2's facets split one dataset into subplots by category, exposing problems that only affect one endpoint, cohort or server.

Example: why do some vector insertions spike?

Cost model of appending to a dynamic array that doubles its capacity when full: each append costs 1, plus copying every element at the moment of doubling. The spikes at 1, 2, 4, 8, 16, 32… are exactly what a plot of real insert times shows — and what a table of averages hides.

Other plot-revealed patterns: periodic latency spikes (garbage collection, cron jobs, traffic), and “system-wide” slowness that's really one category.

10CPU & memory profilers

Tracing

Records every function call

Exact counts, caller/callee relationships — but slow. e.g. Valgrind's callgrind.

Sampling

Snapshots the stack ~every ms

Statistical, low overhead — preferred in production. e.g. perf.

perf — the standard Linux sampling profiler

bash
perf stat ./slow_program      # counters: task-clock, page faults, cycles, branch misses…
perf record -g ./my_program   # sample with call stacks
perf report                   # browse where time went
perf script | stackcollapse-perf.pl | flamegraph.pl > flamegraph.svg

Flame graphs

Y axis = call stack (callers below, callees above). Width = share of samples (time). Wide plateaus at the top are your hot spots. Click a frame to zoom; click the bottom bar to zoom out.

Illustrative profile of the lecture's slow.c.

Interactive viewers: Speedscope (flame graphs in the browser) and Perfetto (whole-system traces). Language-specific profilers: Python cProfile, py-spy; Go go tool pprof; Rust cargo-flamegraph (works for any compiled program). Browsers have their own (Firefox Profiler, Chrome DevTools).

Callgrind (tracing) & Massif (memory)

bash
valgrind --tool=callgrind ./my_program     # exact call counts (+ --cache-sim=yes)
callgrind_annotate callgrind.out.<pid>     # text report  (kcachegrind = GUI)

valgrind --tool=massif ./my_program        # heap usage over time → leaks, excess allocation
ms_print massif.out.<pid>

Python: memory-profiler gives line-by-line memory use.

11Benchmarking with hyperfine

Compare implementations properly: warm-ups, many runs, mean ± σ.

bash
hyperfine --warmup 3 'fd -e jpg' 'find . -iname "*.jpg"'
fd -e jpg — 51.4 ms ± 2.9 ms
find . -iname "*.jpg" — 1.126 s ± 0.101 s
≈ 21.9× slower

Numbers from the lecture's run. Note the System time: find spent ~956 ms in the kernel vs fd's ~160 ms.
